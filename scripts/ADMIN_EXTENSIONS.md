# Расширения админ-панели «Круг Души»

Основные страницы после обновления:
- `/crm/tasks` — внутренние задачи, сроки, ответственные и опциональные уведомления администратору в Telegram.
- `/search` — поиск зарегистрированных пользователей, обращений, подтверждённых платежей.
- `/analytics` — статистика подтверждённых покупок, повторные покупки 30/90 дней и CSV-экспорт.
- `/automations` — обзор сценариев, очередей и сигналов ошибок.
- `/issues` — проблемные отправки, отметки о проверке без опасного автоматического повтора.
- `/operations` — действия администраторов, начиная с внедрения нового журнала.
- `/staff` — владелец создаёт сотрудников и назначает роли.

## Безопасный запуск после обновления

Обычный загрузчик Vultr продолжит выполнять обновление GitHub. Для проверки новых Python- и Jinja-файлов после загрузки:

```bash
cd /opt/dato-telegram
./.venv/bin/python scripts/preflight_extensions.py
```

Рекомендуется открыть в админке по очереди: `/dashboard`, `/crm/tasks`, `/subscriptions`, карточку участника, `/broadcast`, `/search`, `/analytics`, `/automations`, `/issues` и `/staff`.

**Все прежние браузерные сессии владельца должны будут войти заново**, поскольку доступ теперь привязан к версии сессии в БД. Удаление/отключение сотрудника делает его предыдущую сессию недействительной.

## Права сотрудников

- `owner`: полный доступ; существующие учётные записи автоматически получают эту роль для сохранения доступа.
- `admin`: управление основными разделами, без управления пользователями админки и смены учётных данных владельца.
- `support`: только раздел поддержки и действия в нём.
- `analyst`: просмотр главной, журнала событий, аналитики и поиска.

Проверка роли выполняется для каждого HTTP-запроса. При отключении учётной записи уже выданная cookie становится непригодной для защищённых маршрутов. Для WebSocket допускаются только владелец и администратор.

Пароли новых сотрудников — от 12 символов, хранение через существующий хешер проекта.

## Мини-CRM

В карточке подписчика появилась возможность добавить задачу: срок (Тбилиси), ответственный, описание, отметка выполнения и опциональное уведомление.

Уведомления обрабатываются ботом раз в минуту. Они **выключены до указания Telegram ID в /crm/tasks**. Из-за риска дублей отправка выполняется не более одного раза автоматически; неудачи фиксируются в таблице `crm_task_reminder_attempts`.

Массовые метки: на странице подписчиков выбрать до 50 участников на текущей странице, добавить/убрать метку, подтвердить операцию.

Сегменты рассылок: получатели по действующему доступу, постоянному доступу, подтверждённой оплате или конкретной метке. Число получателей пересчитывается при предварительном просмотре, фактические записи фиксируются в очереди одной транзакцией. Отписавшимся рассылки не назначаются.

## Аналитика

Платежи по валютам и системам **не суммируются в единую валюту**. Повторная покупка через 30/90 дней — не то же самое, что удержание члена группы. Платёж должен быть в реестре `verified_payment_receipts`. Экспорт защищён авторизацией.

## Внешние резервные копии — дополнительная настройка

Система ежедневных локальных копий работает отдельно. Для защиты от потери самого VPS добавлены **опциональные** скрипты:

- `scripts/offsite_backup.sh` — загрузка последней свежей копии исключительно в заранее настроенный `rclone crypt` remote, последующая обратная загрузка и побайтовое сравнение.
- `scripts/install_offsite_backup.sh` — установщик таймера резервного копирования после успешной первой проверки.

Требуется **собственное внешнее хранилище и настройка rclone crypt**. Ни ключи, ни пароль не записываются в репозиторий. Без конфигурации таймер не включается.

На сервере после установки rclone и создания зашифрованного remote выполнить:

```bash
sudo bash /opt/dato-telegram/scripts/install_offsite_backup.sh
sudo nano /etc/dato-offsite-backup.conf
sudo bash /opt/dato-telegram/scripts/install_offsite_backup.sh
```

Значение `DATO_RCLONE_CRYPT_REMOTE` должно указывать именно на **crypt remote**, а не на обычный незашифрованный путь. Затем в `journalctl -u dato-offsite-backup.service` можно проверить последнюю попытку загрузки.

Полноценную тестовую восстановительную операцию рабочей БД по-прежнему нужно проводить в изолированной временной базе через `scripts/reliability.py restore-test`, а не в production.
